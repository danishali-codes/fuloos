# PocketBase upgrade for the November 17 app fixes

Use the files from the merged `main` branch. The app changes and PocketBase changes belong together: new contribution, alert-import, net-worth and sharing operations require the integrity hook. Do not deploy only the frontend and assume the server already supports them.

## Using File Station and Portainer

1. Back up the running PocketBase `pb_data` directory, plus the current migration and hook directories. Use your existing backup procedure, so the SQLite backup is consistent.
2. In your existing Portainer stack, inspect the volume mounts to find the host directories mounted as `pb_migrations` and `pb_hooks`. Keep the existing persistent `pb_data` mount and container user/group settings.
3. Download the repository's [`pocketbase/pb_migrations`](pb_migrations) and [`pocketbase/pb_hooks`](pb_hooks) folders. Copy the Fuloos files into those mounted directories with File Station. Preserve unrelated application files and previously installed migrations.
4. Restart the **existing** PocketBase container from Portainer. Its normal startup applies pending migrations in filename order; do not start another instance on the same database.
5. Check the container log for a clean start. In the admin dashboard, verify the new collection and fields below. If startup fails, keep the previous backup and capture the migration error before retrying. Do not run destructive down migrations as a repair.
6. In **Settings → Application**, make sure batch requests are enabled with a maximum of at least **100 requests per batch**. Keep bounded body-size and processing-time limits. Ordinary receipt uploads use the file API, separately from the batch API.

If your server is behind on earlier Fuloos releases, copy **all** current Fuloos migration and hook files, not just this upgrade's additions. The new migrations depend on the earlier goals, captured alerts, net-worth and household collections.

## Dashboard checks

- `fuloos_operations` exists and its list/view/create/update/delete rules are locked. **Do not open these rules to users**; only the authenticated server hooks access it.
- `fuloos_captured_alerts` has `transaction_id`.
- `fuloos_categories` has `household_id`.
- `fuloos_net_worth_snapshots` has `revision`.
- Existing financial records and users are still present.

There are no new secret environment variables for the integrity fixes. Keep **`APP_URL=https://fuloos.danishali.dev`** on the PocketBase container. SMTP is needed for email delivery and email OTP; Google OAuth remains configured on `fuloos_users` with `https://pb.danishali.dev/api/oauth2-redirect` as its redirect URI.

## Verify after restarting

Use a throwaway account first:

- Add a savings contribution with a ledger transaction; confirm there is one contribution and one transaction. A retry of the same operation must not create duplicates.
- Import a pending bank alert; confirm it leaves the pending queue and creates one ledger transaction.
- Create a net-worth item and two valuations, including two on the same date. Delete the latest valuation and check that the previous value becomes current. The last remaining valuation is protected.
- Create a household, share an account and its categories, and test an editor and a viewer. Editors can bulk-edit shared transactions; viewers cannot write. Removing a member removes their access to shared records. Account/budget sharing also shares referenced categories; unsharing an account does not automatically unshare its categories.
- Export a v2 JSON backup, preview it, and restore into a separate test account. Check goals, contributions, rules, card details, valuations, receipts and sharing groups. V1 imports remain supported. Other household members are not automatically invited; push must be enabled again on the restored browser.
- Check a split expense against its category budgets and, if notifications are enabled, compare the resulting budget alert.

## What still needs external configuration

These are integrations, not changes to collection rules:

- **Email capture:** an email worker/forwarder or phone automation must send alerts to the existing capture endpoint using the user's capture token.
- **Push:** configure `PUSH_RELAY_URL`, any relay authentication and VAPID settings on the server, plus `VITE_VAPID_PUBLIC_KEY` on Vercel; rebuild the frontend after changing build variables.
- **Base categorization model:** host the hashed model, set `VITE_LEDGER_MODEL_URL`, and allow that origin in the frontend CSP and the model host's CORS configuration.

The optional browser privacy PIN is not encryption. Workspace backups are plain JSON and may include financial notes, captured-alert text and receipt bytes; keep them private. Authentication secrets, capture tokens, push subscriptions, private ML learning data and other people's household memberships are excluded.
